# Add Hopi to an app

Follow these steps only when the user wants Hopi in their project. Every artifact has the group
`io.github.felipekoga.hopi` and the same version (`0.1.0` at the time of writing; check
https://central.sonatype.com/namespace/io.github.felipekoga.hopi for the latest). Use one version
for every Hopi artifact. Full guide: https://github.com/FelipeKoga/hopi/blob/main/docs/GUIDE.md

Requirements: Kotlin 2.2.0 or newer (2.2.21 for iOS), Gradle 8.0 or newer, JDK 17, AGP 8.0 or
newer with `compileSdk` 34 or higher and `minSdk` 24 or higher.

## 1. Repositories

The plugin is on Maven Central, not on the Gradle Plugin Portal. In `settings.gradle.kts`, add
`mavenCentral()` to both lists:

```kotlin
pluginManagement {
    repositories { google(); mavenCentral(); gradlePluginPortal() }
}
dependencyResolutionManagement {
    repositories { google(); mavenCentral() }
}
```

If the project uses a version catalog, add the entries there and follow its style:

```toml
[versions]
hopi = "0.1.0"
[libraries]
hopi-network = { module = "io.github.felipekoga.hopi:hopi-network", version.ref = "hopi" }
hopi-perf = { module = "io.github.felipekoga.hopi:hopi-perf", version.ref = "hopi" }
[plugins]
hopi = { id = "io.github.felipekoga.hopi", version.ref = "hopi" }
```

Declare the plugin in the same `plugins { }` scope as the Kotlin plugin and AGP (the root
`build.gradle.kts` with `apply false`, or the module).

## 2a. Android (application module)

Apply the plugin to the application module, never to a library (it instruments the libraries from
the app):

```kotlin
plugins {
    id("com.android.application")
    id("io.github.felipekoga.hopi") version "0.1.0"
}

dependencies {
    debugImplementation("io.github.felipekoga.hopi:hopi-network:0.1.0")   // capture and rules
    debugImplementation("io.github.felipekoga.hopi:hopi-perf:0.1.0")      // optional: monitors
}
```

No code is needed. The plugin instruments every OkHttp client and `HttpURLConnection` (Retrofit,
SDKs and Ktor's OkHttp and Android engines included) in debuggable variants. A custom debuggable
build type needs its own `<buildType>Implementation` of the runtimes.

Never declare a runtime as `implementation`: the release guard (`hopiReleaseGuard<Variant>`)
fails a release build that links one, by design. There is no opt-out.

## 2b. iOS (KMP shared module whose framework the app links)

```kotlin
// shared/build.gradle.kts
plugins {
    kotlin("multiplatform")
    id("io.github.felipekoga.hopi")
}

// Top-level dependencies block, not inside kotlin { }.
dependencies {
    debugImplementation("io.github.felipekoga.hopi:hopi-network:0.1.0")
    debugImplementation("io.github.felipekoga.hopi:hopi-perf:0.1.0")      // optional
}
```

Then one line in Swift, first thing at launch, before any SDK setup and with no `#if`:

```swift
// SwiftUI App.init(), or the first line of application(_:didFinishLaunchingWithOptions:)
Hopi.shared.start()
```

`Hopi` is generated by the plugin. It records every URLSession request, Ktor's Darwin engine
included (not CIO). The plugin reads Xcode's `CONFIGURATION`, so the existing
`embedAndSignAppleFrameworkForXcode` build phase needs no change. In Release, `start()` does
nothing and the framework links no runtime. CocoaPods' configuration property is not read.

If the Objective-C header of the framework stops compiling after the change, look for a Kotlin
`const val` whose name is a C macro (for example `NAME_MAX`, `PATH_MAX`) and rename it. Hopi
exports more headers, which can expose a clash that was hidden before.

## 2c. JVM (Ktor)

Add `hopi-ktor` and `hopi-start`, call the start first in `main` before any `HttpClient` is
built, and `install(Hopi)` in each client. The entry and the Ktor plugin are both named `Hopi`, so
import the entry under an alias: `import dev.koga.hopi.start.Hopi as HopiStart`, then
`HopiStart.start()`. The CLI reaches a JVM process with
`--bridge-file <java.io.tmpdir>/hopi/<pid>/bridge.json`. There is no release guard on the JVM: name
`hopi-start` only in builds that should record. See the guide's JVM section.

## 3. Options (optional)

```kotlin
hopi {
    maxBodyBytes = 256L * 1024
    redactHeaders("X-Api-Key")          // more headers to redact; the defaults stay
    network {
        rules = false                   // never apply mock/fail/delay/edit rules
        excludeClasses("com.vendor.pinned.**")
    }
    perf {
        hangThresholdMs = 250
    }
}
```

## 4. Verify

1. Build and install the debug variant, launch the app and make it send a request.
2. `hopi apps` lists the app, and `hopi list` shows the request.
3. Build the release variant: it must pass (`bundleRelease` or the Release scheme). A failure in
   the release guard means that a runtime is declared as `implementation` somewhere.
