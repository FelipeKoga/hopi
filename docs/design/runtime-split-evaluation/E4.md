**2.3 The interface (recommendation).** In `hopi-api` (`commonMain`, package `dev.koga.hopi.rules`), marked
`@HopiInternalApi`:

```kotlin
public interface HopiRulesRuntime {
    // Each add returns the new rule's id. It throws IllegalArgumentException (validation, or no record for `from`)
    // or IllegalStateException (a limit), exactly as HopiRules documents today.
    public fun mock(match: String, rule: HopiMock): Long
    public fun fail(match: String, failure: HopiFailure, rule: HopiRuleOptions): Long
    public fun delay(match: String, rule: HopiDelay): Long
    public fun edit(match: String, rule: HopiEdit): Long
    public fun list(): List<HopiRuleInfo>
    public fun setEnabled(id: Long, enabled: Boolean): Boolean
    public fun remove(id: Long): Boolean
    public fun clear()
}
```

- **What `HopiRules` does in `hopi-api`.** It keeps today's signatures and does three things: builds the builder and
  runs the block (both twins do this today, real `HopiRules.kt:36,52,58,65` and noop `:11,17,23,29`; the noop test
  checks it, `HopiRulesNoopTest.kt:23`); reads the registry field once; then delegates, or returns `-1`, `false` or
  an empty list.
- **What `hopi-core` does.** It implements the interface as `internal object ApiRules : HopiRulesRuntime` in
  `hopi-core/src/commonMain/kotlin/dev/koga/hopi/core/rules/`. The body is today's `HopiRules.kt:35-119`, moved
  verbatim except for two changes: the builders are read through the getters of item 3, and the two enum mappings
  (`HopiRuleBuilders.kt:28-34,45-51`) become `when`s in core. Core can name the API types once it has
  `api(project(":hopi-api"))` (plan 3.3). Core also gets one public `@HopiInternalApi` entry point, for example
  `ApiRules.register()`. It is idempotent: it writes the registry field once and writes the notice of item 4.
- **Exceptions or a result type.** I recommend the runtime throws, as today. That adds no public type to `hopi-api`,
  the code moves verbatim, and the split between `IllegalArgumentException` and `IllegalStateException` stays in one
  place: core's `exception()` (today `HopiRules.kt:88-89`). The other sound option: the runtime returns a small result
  (an id, or a code and a message) and `hopi-api` throws. It costs one more public `@HopiInternalApi` type.
- **`from(id)`.** The runtime resolves the record inside core. Do not keep `HopiStore.default.get` (`HopiRules.kt:41`).
  `HopiStore.default` creates the process store with default caps when none exists (`HopiStore.kt:766-767`), and the
  first store created wins (`:770-779`; `CaptureInstallation.kt:36` goes through `configureDefault`). On Android the
  store is installed lazily, by the first recorded request (`AndroidCapture.kt:87-104`). So `mock { from(n) }` called
  before any request silently fixes the store at 500 entries and 16 MiB, ignoring the plugin's `maxEntries` and
  `maxTotalBytes`. This is a latent bug today (verified by reading; not reproduced). The fix: a lookup that never
  creates a store, for example a `@HopiInternalApi HopiStore.defaultOrNull`, answering
  `mock.fromTransaction: no transaction n` when there is none.
- **When to register: first, and whatever the `rules` switch says.** Register as the first step of the start
  sequence, before the store install and before any tool starts, and also when `rules = false`. That switch keeps its
  current meaning, "the engine and the API stay" (`rules.md:870-872`, `docs/ARCHITECTURE.md:1011-1015`). Registering
  first means a rule added while the tools start still waits for its recorder, as today, and URLSession mirrors it in
  `enable` (`UrlSessionRules.kt:73-82`). Plan 3.4 puts registration after the store install. In that order, invalid
  caps would make `HopiRules` return `-1`; registering first keeps today's behaviour (`HopiRules` works and no recorder
  applies the rules). Either order is acceptable; first is closer to today.
- **Where stage 5 registers, before the start sequence exists.** The call goes first, before the caps checks, so
  invalid caps do not turn `HopiRules` into `-1`. `register()` is idempotent, so repeated `start` calls do no harm.
  - Android: the first statement of `AndroidCapture.start`, before the invalid-caps return
    (`AndroidCapture.kt:120-124`). That covers the provider (`HopiInitProvider.kt:28`) and the host tests that call
    `AndroidCapture.start` directly.
  - iOS: the first statement of core's `UrlSessionCapture.start`, before its caps check (`UrlSessionCapture.kt:116-122`).
    It is reached only when `HopiUrlSession.start` has `enabled = true` (`HopiUrlSession.kt:23-24`), and
    `hopi-urlsession` needs no change.
  - JVM: there is no start path at all once stage 3 has run (see the corrections), so tests call
    `ApiRules.register()`.
  - Stage 7 moves the call into the start sequence, as its first step.
- **A second registration.** `hopi-api` cannot write the "ignored with a notice line" of plan 3.3: it has no log
  sink. Its register function returns `false` (or `null`) and the runtime that called it writes the line.
- **Versions.** The interface is internal API shared by two artifacts that resolve separately: `hopi-api` from the
  app, and `hopi-core` from the plugin's runtime at `HOPI_VERSION` (`HopiPlugin.kt:128,135`). A version mismatch fails
  at run time (`AbstractMethodError` or `NoSuchMethodError`). In stage 7 the plugin should add a constraint that
  aligns `hopi-api` with its own version in debuggable variants.
- **Swift.** `hopi-api` is exported, so its public `@HopiInternalApi` declarations reach Swift: `@RequiresOptIn`
  does not apply there. Evidence: today's header already lists core's `@HopiInternalApi` perf types (`Shared.h:9`,
  e.g. `SharedHopi_corePerfData`; compare `hopi-core/src/commonMain/kotlin/dev/koga/hopi/core/perf/PerfData.kt:12,16`).
  Mark the registry, `HopiRulesRuntime` and the getters of item 3 `@HiddenFromObjC` (`kotlin.native`, with
  `@OptIn(ExperimentalObjCRefinement::class)`). (Unverified: that this annotation works from `commonMain`; experiment
  X2.)
- **Thread safety.** One `AtomicReference` per runtime kind, from the stdlib's `kotlin.concurrent.atomics` as in
  `RuleEngine.kt:4-7`. `hopi-api` then needs `optIn.add("kotlin.concurrent.atomics.ExperimentalAtomicApi")`, as
  `hopi-core/build.gradle.kts:17` has. No expect/actual is needed; it is one volatile read on the JVM and ART.
- **Exceptions in Swift are unchanged.** A validation error thrown inside `HopiRules.shared.mock` called from Swift
  is an unhandled Kotlin exception, since nothing has `@Throws`. (Unverified that Kotlin/Native then terminates the
  app; not run.) Adding `@Throws` would change the Swift signatures. That is the owner's call and the split does not
  need it.

**2.4 What D2 changes inside `core/rules` (verified by reading; this is stage 3 work, and it has to land before
stage 5 moves the tests).**
- What goes: `RuleSource.KTOR` (`RuleModel.kt:12`), the Ktor exemption in `Capabilities.unsupportedOn`
  (`Capabilities.kt:51-56`), the Ktor sentence in the KDoc of `appliesNowhere` (`:67-73`), and the Ktor members of the
  three `platformSources` (`PlatformSources.android.kt:3-4`, `PlatformSources.ios.kt:3-4`,
  `PlatformSources.jvm.kt:3-4`).
- **The JVM's `platformSources` becomes empty** (nothing records on the JVM, O5). For a rule that names no sources,
  `Capabilities.unsupported` then reports nothing and `appliesNowhere` returns true, because `emptySet().none { }` is
  true (`Capabilities.kt:74,76`). The in-app list would read such a rule as "inactive" (`RulesPane.kt:73`), which only
  hopi-ui's JVM tests reach. Recommendation: keep it, since it is accurate (the JVM has no source), and rewrite the
  tests that assume Ktor (`CapabilitiesTest.kt:13-18,28-30`, `RuleEngineTest.kt:101`).
- **iOS becomes more accurate.** With `platformSources = {URL_SESSION}`, a response edit or a before-response delay
  that names no sources now reads "inactive", so the caveat in `rules.md:853-856` goes away.
- **The iOS hit counter depends on the URLSession C library.** Counters are created by
  `CompiledRule.kt:13-14` → `HitCounter.ios.kt:15,26` (`hopi_us_hits_new`), and the mirror casts them
  (`UrlSessionRules.kt:132`). A failed cast is swallowed by the `catch` in `mirror` (`:100-101`), so the rule silently
  never reaches URLSession. If E2.6 moves the URLSession library out of core, core's iOS engine loses its counter.
  Core would then need `AtomicHitCounter` on iOS by default, and the network tool would have to install the native
  counter factory before the first rule exists (that is, before the rules runtime registers), or the mirror would
  have to allocate its own counters. This is input for E2.6.

**Recommendation: `@HopiInternalApi` read-only getters, about 19 of them, not one snapshot method per builder.**
- The builders are already one-shot: created per call, read once by the runtime during that call, and converted to
  immutable core specs (`RuleSpec` and its parts, `RuleModel.kt:105-185`), as today (`HopiRules.kt:35-67`). A snapshot
  method would add a second set of public classes that repeat the same fields. That is more ABI and more Swift header
  for no benefit.
- Pick names that cannot clash with the consumer API or with Objective-C accessors, so no `set*` or `add*`. For
  example: `ruleSources`, `queryPredicates`, `headerPredicates`, `delayBeforeRequest` and `delayBeforeResponse` (on
  the options class, since `HopiDelay` already uses `beforeRequest`), `headerList`, `bodyBytes`, `fromTransactionId`,
  `requestEdit`, `responseEdit`, `querySets`, `queryRemovals`, `headerSets`, `headerAdds`, `headerRemovals`.
- **Semantics the runtime must keep, verbatim from today:**
  - (a) In `HopiRules.delay`, when `beforeRequest` or `beforeResponse` is positive, the two vars replace whatever
    `delay()` set (`HopiRules.kt:59`). Negative values are ignored there, and the call then fails with "needs a
    non-zero delay" (`RuleValidation.kt:47`).
  - (b) A null delay and a zero delay are the same for validation and for the record mark (`RuleValidation.kt:41-47`,
    `RuleModel.kt:172`). But negative values given to `delay()` must still reach validation
    (`RuleValidation.kt:42-43`), so keep "null until called" rather than "zero means none".
  - (c) `MockSpec(status ?: 200, …)`, and the fields set on the builder overriding the record when `from` is used
    (`HopiRules.kt:38-46`).
  - (d) `sources()` replaces; predicates and headers add up; `request { }` and `response { }` add up
    (`HopiRuleBuilders.kt:73-75,155,159`).
- Do not encode predicates as shorthand strings for `MatchShorthand.predicate` (`MatchShorthand.kt:95-99`). A name
  that contains `=` or starts with `!` would parse differently from today's direct `Predicate(name, value)`
  (`HopiRuleBuilders.kt:79`).
- **The ABI dump.** KGP 2.4.20 has `AbiFilterSetSpec.annotatedWith`. I verified this from the strings of
  `org/jetbrains/kotlin/gradle/dsl/abi/AbiFilterSetSpec.class` in
  `~/.gradle/caches/modules-2/files-2.1/org.jetbrains.kotlin/kotlin-gradle-plugin-api/2.4.20/…/kotlin-gradle-plugin-api-2.4.20-gradle96.jar`,
  which contain `annotatedWith` and `byNames`. So
  `abiValidation { filters { exclude.annotatedWith.add("dev.koga.hopi.core.HopiInternalApi") } }` keeps the dump
  equal to the consumer API, the same idea as `hopi-android/build.gradle.kts:21-27`. (Unverified: that exclusion
  works on members and not only on classes; experiment X1.)
- **Cost in release.** Once the builders keep and copy what they are given, they do so in release builds too, where
  the noop dropped it. So the plan's 3.7 line "API calls without a runtime: one volatile read, nothing else" is not
  exact for rules: the block runs, and `body(bytes)` copies the bytes it is given. That is negligible for an API meant
  for tests and debug menus. Either say so in 3.7, or (option) let the builder skip storing when no runtime is
  registered: one boolean per builder, with the public vars still reading back what was set
  (`HopiRulesNoopTest.kt:34-41`).
- **The moved annotation trips the release checks.** Stage 4 moves `HopiInternalApi`
  (`dev.koga.hopi.core.HopiInternalApi`, `hopi-core/src/commonMain/kotlin/dev/koga/hopi/core/HopiInternalApi.kt:1,19`)
  into `hopi-api`. In stage 5, `hopi-api` reaches the release APK through `sample/shared` `commonMain`.
  - Android: the release check forbids every type under `dev/koga/hopi/core/`
    (`sample/androidApp/build.gradle.kts:143-144,180`), and it reads every dex `type_id` (`DexReader.kt:24,88`). The
    sample's release build declares no minification: `buildTypes` has only `debug`
    (`sample/androidApp/build.gradle.kts:33-39`). (Unverified: that AGP 9.4's default for `isMinifyEnabled` is
    false; X3 settles it.) If so, the annotation class is defined in the APK and `verifyReleaseUsesNoop` fails.
    (The check's logic is verified by reading; the failure itself is unverified: X3.)
  - iOS: `coreSymbols` counts every `kfun:dev.koga.hopi.core` symbol (`sample/shared/build.gradle.kts:161,180`). An

#### 4. Calls made before registration: a notice line, not a queue

**Recommendation.** The four add calls (`mock`, `fail`, `delay`, `edit`) made while no rules runtime is registered
return `-1`, as in release, and each one increments a counter in the registry. When the rules runtime registers, it
reads the counter and writes one notice line, for example
`{"hopi":1,"notice":"HopiRules: 2 rules added before Hopi started were dropped (their calls returned -1)"}`. That is
the format of `AndroidCapture.notice` (`AndroidCapture.kt:149`). `list()`, `setEnabled`, `remove` and `clear` are not
counted: a `clear()` in a test teardown before start is normal. `hopi-api` writes nothing itself.

**Why not a bounded queue** (each point verified):
1. **The contract is synchronous.** An add returns the engine's id and throws on bad input (`HopiRules.kt:26-28,35-48`;
   tested in `HopiRulesTest.kt:105-114`). A queued rule has no engine id yet (ids come from `RuleEngine.kt:70,106`)
   and the API cannot validate it (validation belongs to core, plan 3.3). So the call either returns `-1`, and then
   `remove` and `setEnabled` cannot address the rule, or it returns a provisional id that the engine must adopt
   through a new entry point. And an invalid queued rule fails after its call has already returned.
2. **`list()` would need logic in the API.** It would have to describe drafts nobody validated, but `match`, `action`
   and `unsupported` are computed by core (`HopiRules.kt:91-102`).
3. **Release builds never register a runtime.** The queue would fill to its bound and keep builders and bodies for the
   life of the process. Bounding it means copying the engine's limits into the API: 64 rules, 1 MiB per body, 8 MiB
   in all (`RuleValidation.kt:8-10`).
4. **Draining races with new calls.** Calls arriving after registration compete with the drain (the order of ids, a
   `clear()` during the drain), so the API would need a lock.
5. **The window is tiny.**
   - Android: the provider has `initOrder="2147483647"` (`hopi-android/src/androidMain/AndroidManifest.xml:11`) and runs
     before `Application.onCreate` (`HopiInitProvider.kt:15-16`). Only code in the `Application` constructor, in
     `attachBaseContext`, or in another provider with the same top `initOrder` runs before it.
   - iOS: `start` is the first statement (plan 3.2; the sample does this in `sample/iosApp/iosApp/iOSApp.swift:6-10`).
   - JVM: tests register first.

**Why the runtime writes the notice, not the API.** `hopi-api` has no dependency, so it has no log sink (core's is
`emitPlatformLogLine`). It also cannot tell a Release build from one that has not started yet. A notice written by the
API would print in every release build that calls `HopiRules`, for example from a debug menu compiled into release.

Details:
- **No match text in the notice.** A match can carry query or header values (`?token=…`,
  `matchHeader("Authorization", …)`) that every other surface redacts (`RuleJson.kt:303` `describeMatch`, used by
  `RulesPane.kt:76`; the redacted predicates are written at `RuleJson.kt:295-298`).
- **A race to accept.** A call that reads "no runtime" while registration is running is dropped and may miss the
  count. It is never applied wrongly.
- **The notice's switch** should follow the same rule as the start sequence's other error notices; E2.2 decides it.
  Today Android writes notices only with `summaryLog` on (`AndroidCapture.kt:122`), while iOS always writes the
  invalid-caps one (`UrlSessionCapture.kt:119`).
- **A behaviour change to document in stage 5.** Today a rule added before any recorder is kept and applies once one
  starts (`rules.md:815-817`; URLSession mirrors the existing rules in `enable`, `UrlSessionRules.kt:73-82`). After the
  split, only calls made after the start sequence registered the runtime are kept. Registering as the start
  sequence's first step keeps the rest of that guarantee.
- **The plan's risk table (section 8) cannot work as written.** Its row "A forgotten iOS start call" relies on "a
  notice when the API is used with no runtime registered". The runtime cannot write that, since nothing registers.
  The API could write it only on iOS, and only with a build-type signal: `kotlin.native.Platform.isDebugBinary` would
  let `hopi-api`'s `iosMain` write one `NSLog` line per process in debug binaries. (Unverified: experiment X5.) This
  is optional; on Android the start cannot be forgotten (D5).
- **Perf (E5)** can use the other option of plan 3.4: one pending `HopiPerf.start` configuration is bounded by
  construction. The registry can behave differently per runtime kind.
