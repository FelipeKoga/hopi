**2.3 Fixture design and recommendation**

Recommended: **a shared test source directory, `testing/fixtures/` at the root, added with
`kotlin.srcDir(rootProject.layout.projectDirectory.dir("testing/fixtures"))` to each consumer's test
source set**, the precedent the repository already uses for `benchmark/fixtures`
(`hopi-cli/build.gradle.kts:28`, `hopi-core/build.gradle.kts:54`, `hopi-ui/build.gradle.kts:68`;
verified). Common Kotlin only, public `@HopiInternalApi` core API only, `@file:OptIn(HopiInternalApi::class)`,
declarations `internal` (each module compiles its own copy; no test classpath sees two copies).
First consumer `hopi-cli` (test); then `hopi-connect`, `hopi-desktop` (test) and `hopi-ui`
(commonTest) can replace their copies.

Why not the plan's two options: a `@HopiInternalApi` helper in `hopi-core` ships test code in every
debug app and core has no ABI check to guard it (no `abiValidation` in `hopi-core/build.gradle.kts`,
no `hopi-core/api/`; verified); a non-published module needs its own targets (all four if
`hopi-ui` commonTest uses it, so it compiles for iOS in `check`), a `settings.gradle.kts` include and
care to stay out of `publishedModules` (`build.gradle.kts:244-258`) for the same result. Revisit
the module if the fixtures grow (fake bridge peers, perf events).

#### 4. Content-Encoding

**4.1 Android: 3.8.1 confirmed** (verified for OkHttp; Android's own `HttpURLConnection` by documentation only)

- `HopiOkHttpInterceptor` is the last application interceptor (`HopiOkHttpInterceptor.kt:31-33`), above `BridgeInterceptor` (`docs/design/rules.md:437-439`): OkHttp decodes gzip only when it added `Accept-Encoding` itself.
- Tests: app-named `Accept-Encoding: gzip` → the OkHttp record holds `1f 8b` and `Content-Encoding: gzip` (`AndroidRulesTest.kt:94-102,299-311`); the same for `HttpURLConnection` (`:586-597`, "HttpURLConnection never decodes a gzip the app asked for itself"); OkHttp's own gzip is recorded decoded (`AndroidCaptureTest.kt:132-139`); today the plugin hides it: `PlatformCapture.kt:15-22`, `Hopi.kt:81-89,106-109`, `AndroidCaptureTest.kt:477-495`.
- Caveat: the host tests run the JDK's `sun.net.www.protocol.http.HttpURLConnection` (`AndroidCaptureTest.kt:446`), which never adds `Accept-Encoding`; Android's own connection decodes transparently when it asked, as `BodyDecoding.kt:11-13` states (unverified here: device behaviour, experiment R2).

**4.2 iOS: very likely unaffected** (unverified: no test sets its own `Accept-Encoding`)

- The capture test covers only URLSession's own `Accept-Encoding` (`hopi-urlsession/src/iosTest/.../UrlSessionCaptureTest.kt:398-405`, `/gzip` from `hopi_fixtures.m:163-165`): recorded decoded.
- Indirect evidence: Ktor's Darwin engine builds response headers in `DarwinResponseUtils.kt readHeaders` and calls `dropCompressionHeaders` (klib IR string table), the helper "for engines which apply decompression but don't drop compression headers" (`.reference/ktor-3.5.2/ktor-client-core/commonMain/io/ktor/client/utils/HeadersUtils.kt:13-31`). Ktor itself relies on URLSession always decoding, including under `ContentEncoding`. The plugin covers Darwin with `cover`, not `coverWithPassThrough` (`UrlSessionCapture.kt:143`). URLSession records keep the raw `Content-Encoding` header over a decoded body, which is why `heldCodings` excludes them (`BodyDecoding.kt:14-15,18`).

**4.3 Lazy decoding spec (O4)**

- *What exists* (verified): `DECODABLE_CODINGS = gzip, x-gzip, deflate` (`BodyDecoding.kt:7`); `heldCodings(tx)` (`:17-24`) returns the codings a record still holds, from `source ∈ {okhttp, urlconnection}` plus the response `Content-Encoding` header; `decodeBody(coding, bytes, maxBytes)` (`:26-34`), bounded at `maxBytes + 1` in one doubling array (`BodyDecoding.jvm.kt` and `.android.kt:10-55`, same code); iOS returns null (`BodyDecoding.ios.kt:4`). Only user: the mock copy (`RuleJson.kt:115-123,139-150`), whose bomb bound is tested (`EncodedBodyMockTest.kt:100-126`, under 2x the limit + 512 KB).
- *Encoded flag and `Content-Encoding` value*: no field on `CapturedBody` (`HttpTransaction.kt:20-31`) and none needed. `heldCodings(tx)` is both the flag (non-empty) and the value, because the header is recorded anyway (`HopiOkHttpInterceptor.kt:228`) and crosses the bridge in `get` (`TransactionJson.kt:267-271`), so hosts derive the same answer. It depends on OkHttp and `HttpURLConnection` dropping `Content-Encoding` when they decode themselves (the body half is tested, `AndroidCaptureTest.kt:132-139`; the header half is OkHttp's `BridgeInterceptor` behaviour, unverified here, no OkHttp sources in the repo). Add a field only if a future recorder cannot keep that invariant. A mock that names `Content-Encoding` over a plain body fails to decode and falls back to the raw view.
- *Missing pieces*: (1) promote `heldCodings`, `decodeBody` and `DECODABLE_CODINGS` to public `@HopiInternalApi` in `dev.koga.hopi.core.body` (they are `internal` in `core.rules` today, unreachable from `hopi-ui`, `hopi-cli`, `hopi-desktop`); (2) a prefix mode: a held body truncated at the cap is a cut gzip stream, and `GZIPInputStream`'s `EOFException` (an `IOException`) makes `decodeBody` return null (`BodyDecoding.jvm.kt:16-19`), so `readAtMost` must return what it inflated before the cut, marked incomplete; (3) the display cap, which the UI does not have (the store knows only `maxEntries`/`maxTotalBytes`, `HopiStore.kt:57-69`; the cap lives in `CaptureInstallation.Installed.maxBodyBytes`, `CaptureInstallation.kt:22,49`).
- *Cap*: capture caps the bytes the stack hands over, the encoded ones (`HopiResponseBody`/`TeeSource`, `HopiOkHttpInterceptor.kt:376-379,409-421`), so `totalBytes`/`truncated` describe encoded bytes and the store counts only them (`HttpTransaction.kt:141-143`). Decoded output: at most the per-body cap in the app, which is what the plugin kept (`BoundedBuffer(maxBodyBytes, …)` on the decoded stream, `Hopi.kt:264`); on hosts a host bound (16 MiB), since `hello` does not carry the app's cap (`BridgeSession.kt:787-803`). Over the bound: "decoded first N bytes". `br`, `zstd`, stacked or unknown codings: "encoded (br), N bytes" (the mock path already refuses them the same way, `RuleJson.kt:120-123`).
- *Where it runs*:
  - In-app screen and desktop panes: one call site, `DetailFormatter.formatBody` (`DetailModel.kt:234-266`, before `textOrNull()` at :254), already off the main thread (`withContext(formatDispatcher)`, `Dispatchers.Default`, `HopiScreen.kt:114,299`), cached by body instance (`DetailModel.kt:140-160`, 4M-char budget :166-171). `bodyView(body, side)` must receive the codings, since the body alone does not carry them. Copy and share read the view (`shareTextOf`, `DetailModel.kt:310`).
  - CLI human `get`: `Render.kt:175-202` (today a gzip body prints "binary … --json has it as base64").
  - HAR: `SessionExport.kt:131-149,176-187`. HAR 1.2 wants `content.text` decoded, `content.size` decoded, `bodySize` encoded, `content.compression` = size − bodySize.
  - Bridge `get`: keep sending the held bytes (`TransactionJson.kt:259-289`). The device pays nothing and the protocol stays 1. Hosts decode with the JVM actual. Alternative: decode in the app on the bridge writer (`BridgeSession.kt:810` "encoded only when written") with additive fields, so `hopi get --json` readers (agents) see text. That costs the device up to 2x the cap per `get`; the owner decides.
  - cURL: nothing. It reproduces the request (`Curl.kt:25-56`) and already adds `--compressed` when the request advertises compression (`Curl.kt:32,44,51`).
- *Memory bound for a giant body*: the decoder allocates at most about 2x the bound in all (doubling from 8 KB, last step straight to bound + 1; test `EncodedBodyMockTest.kt:115-126`). A gzip bomb is bounded the same way whatever its ratio. Then the text and formatter cost as for any body (about 4.4x for minified JSON, `README.md:484`) inside the 4M-char cache. Default cap 256 KiB: under 0.6 MB to decode. Raised cap of 16 MiB: up to about 32 MiB transient, off the main thread, the same order the plugin held decoded.

#### 6. Wire compatibility of removing `"ktor"` (O3)

- `hello` carries `"protocol": 1` (`BridgeSession.kt:787-803`, `PROTOCOL_VERSION = 1` at :835), and hosts require exact equality (`BridgeClient.kt:63-64`: "the bridge speaks protocol $protocol; this CLI speaks $PROTOCOL"). Do not bump it: dropping a value from the additive `source` field breaks no reader, while a bump would make every mixed old/new pair refuse to connect (verified).
- Decoders are lenient (verified): transactions keep `source` as a raw string (`BridgeDecoder.kt:54,86`), the CLI prints it raw (`Render.kt:46`), the UI shows unknown values as sent (`Text.kt:43-50`), HAR writes `_source` raw (`SessionExport.kt:162`), the summary line cuts it at 13 chars (`TransactionJson.kt:18,228`). Host rule lines keep `sources` and `unsupported[].source` as strings (`RuleClient.kt:175-195`).
- Strict points (verified): the app's `RuleJson` rejects an unknown name, `match.sources: unknown source '$name'` (`RuleJson.kt:48-50`), so an older CLI or desktop sending `"ktor"` gets `BAD_REQUEST`; the CLI `--source` (`RuleArgs.kt:37-38`) and the desktop form (`RuleForm.kt:132-133`) use `RuleSource.of`, and their error texts list `ktor` (also `CliArgs.kt:225`, `RulesPanel.kt:338`, `README.md:340`, `docs/design/rules.md:771`).
- Fixtures (verified): no recorded fixture carries `"source":"ktor"`. `benchmark/android-capture/2026-10-24/e2e/capture-cli.ndjson` has 9 `okhttp` + 12 `urlconnection`; the other NDJSON files under `benchmark/` carry no `source`; no test resource has transaction lines; the inline test lines that name `ktor` are rule lines (`RuleClientTest.kt:127`, `RuleFormTest.kt:42`, `RuleSpecTest.kt:145`).
- Recommendation confirmed, refined: remove `TransactionSource.KTOR`, `RuleSource.KTOR`, `HopiSource.Ktor`; keep the decoders as they are; drop the `!= "ktor"` filters (`Render.kt:46`, `TransactionRows.kt:111`) so an older app's records show `[ktor]`. Put one shared parser in core (for example `RuleSource.parse(name)`) used by `RuleJson.kt:49`, `RuleArgs.kt:38` and `RuleForm.kt:133`: for `ktor` it fails with "'ktor' is no longer a source: Ktor's engines are recorded as okhttp (OkHttp engine), urlconnection (Android engine) or urlsession (Darwin engine)", otherwise "unknown source 'x' (okhttp, urlconnection, urlsession)". In the CLI that is a usage error (exit 1, as `RuleCliTest.kt:111` checks for `cronet`); in the app it is a `BAD_REQUEST` whose message reaches an older host's user. Keep `run.py:183-184` as a cheap guard. Rename the `hopi-ktor`/`noop-ktor` run labels (`benchmark/urlsession/e2e/run.sh:25,29`, `check.py:191,219`) to `ktor-darwin`.
