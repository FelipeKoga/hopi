   a. **Owners Compose needs.**
   - **Required: `ViewTreeLifecycleOwner` and `ViewTreeSavedStateRegistryOwner`.** `AbstractComposeView.resolveComposeViewContext` throws `IllegalStateException("Composed into the View which doesn't propagate ViewTreeLifecycleOwner!")` and `"…ViewTreeSavedStateRegistryOwner!"` when they are missing. (verified, [CUI] bytecode)
   - **Optional: `ViewTreeViewModelStoreOwner`.** It is read but may be null, with no throw. (verified, [CUI])
   - **hopi-ui needs no `ViewModelStoreOwner`.** It uses no `viewModel`/`LocalViewModelStoreOwner`. (verified, `rg` in `hopi-ui/src`)
   - **The owners are looked up from the nearest ancestor that holds the owner tags** (`findViewTreeComposeViewRoot`). Setting them on Hopi's own view isolates Hopi from what the app put on the decor. (verified, [CUI])
   - **Back handling needs one more owner.** `HopiScreen`'s `BackHandler` (`HopiScreen.kt:160`) is ui-backhandler's. On Android it calls `androidx.activity.compose.BackHandlerKt.BackHandler` (verified, [BH] bytecode). That function throws `IllegalStateException("No NavigationEventDispatcherOwner … and no OnBackPressedDispatcherOwner …")` without one of them (verified, [ACO]). So `HopiScreen` can only be composed where an `OnBackPressedDispatcherOwner` exists, such as a `ComponentActivity`. The button does not need one.
   - **`ComponentActivity`** sets six owners on the decor view: lifecycle, ViewModelStore, saved state, OnBackPressed, FullyDrawn, NavigationEvent. It does this in `initializeViewTreeOwners()`, which `setContentView(…)` ×3 and `addContentView` call. (verified, [ACT] `ComponentActivity`)
   - **`ComponentActivity.setContent`** sets the lifecycle, ViewModelStore and saved-state owners on the decor only when they are absent (verified, [ACO] `setOwners`). Never write Hopi's owners on the decor, or the app's own composition would use them.
   - **A plain `android.app.Activity`** has no owners.
   - **Recommendation.**
     - Give the overlay its own owner object, set on the overlay view itself: an own `LifecycleRegistry` mirroring the activity, plus an own `SavedStateRegistryController`. Mirror the activity from its `Lifecycle` for `LifecycleOwner` activities, and from the tool's `ActivityLifecycleCallbacks` for the others.
     - This needs no ViewModelStore and never touches the app's saved state.
     - Constraint: the registry must be created and `performAttach()`/`performRestore()`d while Hopi's lifecycle is still INITIALIZED. `performAttach` throws "Restarter must be created only during owner's initialization stage", `performRestore` throws "performRestore cannot be called when owner is …", and `consumeRestoredStateForKey` throws before CREATED (verified, [SS] `SavedStateRegistryImpl`). So the activity's own lifecycle cannot back a fresh registry attached after `onCreate`.
     - Send ON_DESTROY at `onActivityDestroyed`, so the window recomposer created from this lifecycle stops with it. The signature `createLifecycleAwareWindowRecomposer(View, CoroutineContext, Lifecycle)` is verified ([CUI]). That it cancels on ON_DESTROY is (unverified: inferred, the method body was not read).
     - Each direct child of `android.R.id.content` gets its own `Recomposer` (`getWindowRecomposer` → `getContentChild`, the child of id `16908290`, verified, [CUI]). The overlay therefore never recomposes with the app.
     - hopi-ui already reaches `androidx.activity:activity-compose`, and with it `activity`, lifecycle and savedstate. `ui-backhandler-android` declares it as an api dependency (verified, [BH] `.module`, `androidApiElements`: `androidx.activity:activity-compose 1.8.0`).

   b. **When and where to attach.** The plan says "for each created activity". That is the wrong moment.
   - **`onActivityCreated` comes too early.** It is dispatched from the base `Activity.onCreate` (`[AOSP] android/app/Activity.java:1720`), that is, inside the app's `super.onCreate()`. The sample calls `super.onCreate` at `MainActivity.kt:96` and `setContent` at `:128`.
   - **`setContentView` then removes every child of the content frame** (`[AOSP] com/android/internal/policy/PhoneWindow.java:495-499`; `setContentView(int)` at `:466-467`).
   - **`setContent` takes over a `ComposeView` at child 0.** `ComponentActivity.setContent` does `findViewById(android.R.id.content).getChildAt(0)`. If that is an instance of `ComposeView`, it puts the app's content into it (verified, [ACO] `ComponentActivityKt.setContent`, offsets 7-31).
   - **Touching the content frame early installs the decor before the app's `onCreate` body runs** (`[AOSP] android/view/Window.java:1579-1581`; `PhoneWindow.java:2152-2157`).
   - **`onActivityPostCreated` runs after `onCreate`** (`Activity.java:8606`), but it is API 29 (`[API] :6388`). minSdk is 24 (`gradle/libs.versions.toml:27`).
   - **Recommendation.**
     - Attach on `onActivityResumed`, idempotently (no overlay yet, or overlay parent ≠ content frame), as the last child of `android.R.id.content`. This runs before the first frame on the first resume, since the window is attached after resume.
     - Show it on resume and hide it on pause (`visibility`). One button is then visible even with a translucent activity on top (the one below is paused), and none in picture-in-picture (the activity is paused).
     - Remove it on `onActivityDestroyed`.
     - Re-attach (posted) from an `OnAttachStateChangeListener.onViewDetachedFromWindow` when a later `setContentView` removed it and the activity is not finishing.
     - Make the overlay a subclass of `AbstractComposeView`, not `ComposeView`. Then even as child 0 it fails `setContent`'s `instanceof ComposeView` check and is never taken over.
     - On resume, call `bringToFront()` when it is no longer the last child (an app view added later would cover it).
     - Avoid `setOnHierarchyChangeListener` (single slot, it would replace the app's).
     - All of this is (unverified on a device: [run] below).

   c. **Overlay size and touches.** The plan wants "the button only, never a full-screen view". The code argues the other way:
   - `AndroidComposeView.dispatchTouchEvent` returns `ProcessResult.dispatchedToAPointerInputModifier` (bit 0 of `handleMotionEvent`'s result). A DOWN that hits no pointer-input node returns `false`. (verified, [CUI] bytecode, method tail at offsets 368-378)
   - `ViewGroup` offers a DOWN to its children from the top down. It stops at the first child that returns `true` and otherwise moves to the next child below (`[AOSP] android/view/ViewGroup.java:2711,2744,2760-2762`). (verified)
   - The only pointer-input nodes of the button content are the 48 dp circle (`HopiLauncher.kt:226-244`). The full-size box (`:205-211`) and the HUD (`PerfHud.kt:205`; "it takes no touch", `ARCHITECTURE.md:2016`) have none. (verified)
   - **The existing button code requires the full area.** The drag range and offset come from the full-size box's size (`HopiLauncher.kt:204-221,235-240`). The HUD is a full-width strip.
   - **Recommendation.** A `MATCH_PARENT` overlay that composes today's `LauncherButton` and `PerfHudHost` unchanged, with `onOpen` launching the inspector activity. A button-sized view would need new drag code (moving the view) and a second view for the HUD.
   - Accessibility hover / explore-by-touch outside the button is (unverified: hover dispatch not read).

   d. **Insets.**
   - On API 30+ with targetSdk ≥ 30, `ViewGroup` gives every child the same insets. Below that, or with targetSdk < 30, the legacy loop stops at the first child that consumes them (`[AOSP] android/view/ViewGroup.java:7370-7399`; `View.java:1020-1027,5550`). (verified for the API 34 source; on API 24-29 devices the legacy loop is the only one, per that comment)
   - Compose does not consume by default: `consumeWindowInsets` defaults to `false` (`WindowInsets_androidKt.getConsumeWindowInsets` returns false for no tag; `WindowInsetsHolder.consumes` defaults to false; `InsetsListener` returns `CONSUMED` only then). (verified, [FL] 1.12.1; older foundation-layout versions may differ, unverified)
   - **Risk:** API 24-29, edge-to-edge window, and an app root that consumes insets (a `fitsSystemWindows` View root, or `consumeWindowInsets = true`). There the overlay gets no insets and the button can sit under a bar.
   - **Mitigation if the run shows it:** feed the overlay `ViewCompat.getRootWindowInsets(decor)` on attach and on each change.
   - Non-edge-to-edge windows are safe: the decor already insets the content frame. (unverified: decor layouts not read)
   - IME: `safeDrawing` includes the IME, so the button moves above the keyboard as today.

   e. **Other cases.**
   - **Dialog-themed activities** (`window.isFloating`): skip them, no button inside a dialog window.
   - **Translucent full-window activities:** they get the button, and the paused activity below hides its own.
   - **Dialogs, sheets and popups** are separate windows above the activity. The button is under them and unreachable while a modal dialog is up. Document it.
   - **PiP:** hidden (paused).
   - **Multi-window:** one button per resumed activity (API 29+ multi-resume).
   - **Hopi's inspector activity:** skip.
   - **`NativeActivity`:** skip (it takes the surface).
   - **Owner checks:** use interface checks (`is LifecycleOwner`), never class names (`androidx.core.app.ComponentActivity` is a `LifecycleOwner` without saved state).
   - All (unverified: policy, [run]).

   f. **Process death and the saved launcher position.**
   - **The saved-state key.** Compose keys a view's saved state by the `AndroidComposeView`'s parent: `R.id.compose_view_saveable_id_tag` if it holds a String, else its `getId()`, giving `"SaveableStateRegistry:<id>"`. It registers only when no provider exists under that key, and otherwise saves nothing for that view. (verified, [CUI] `DisposableSaveableStateRegistry(View, owner)` offsets 0-62 and the String overload offsets 49-87; `AndroidComposeView` passes itself; `Wrapper_androidKt.setContent` adds the `AndroidComposeView` into the `AbstractComposeView`)
   - **The collision.** The app's `setContent` view has the default id (−1). An overlay with the default id, on the activity's registry, shares that key. If Hopi's overlay registers first (an app that sets content late), the app's own `rememberSaveable` state is silently not saved. If it registers second, Hopi's position is not saved.
   - **Recommendation.**
     - Use Hopi's own registry (a. above), so no collision is possible.
     - Keep the position as fractions (as today) in a process-wide holder in the UI runtime, so the button keeps its place across activities. Today it is per launcher instance.
     - It resets after process death, unless it is persisted (SharedPreferences `apply()` on drag end). Owner's choice.
     - `open` no longer exists: Android restores the inspector activity itself after process death. Its `rememberSaveable` selection comes back against an empty store and shows the "missing" detail, which is today's behaviour too.

4. **`HopiInspector.open()`: what the UI runtime registers and how it presents**
   - **Registration.** The UI tool, when it starts, writes one `@HopiInternalApi` object into the registry's `inspector` field (3.3), for example `fun open()`.
   - **Behaviour.** `HopiInspector.isAvailable` is `registry.inspector != null`, and `open()` does nothing without it. Recommended: one notice line, once per process, when it is called with no runtime. That follows the plan's "not lost silently" rule (3.4 end).
   - **Threading.** `open()` may be called from any thread. The runtime posts to the main thread: `Handler(Looper.getMainLooper())`, or `dispatch_async(dispatch_get_main_queue())`.
   - **Android.** It starts `HopiInspectorActivity` (2g):
     - from the tracked resumed activity when the launcher is on;
     - otherwise from the application context with `FLAG_ACTIVITY_NEW_TASK` (`Platform.android.kt:42-43` pattern). With the launcher off, the tool then needs no lifecycle callbacks at all.
   - **The launcher button** calls the same path.
   - **Repeated calls.** `singleTop` keeps them from stacking inspectors.
   - **iOS.** It picks the foreground-active scene with the key window and presents the inspector controller (`ComposeUIViewController { HopiScreen(HopiStore.default, onClose = dismiss) }`) `.fullScreen`. Use Hopi's window (3b-A), or the app's top controller as the fallback in 3c. Hide the launcher overlay while open; today the button is not composed while open, `HopiLauncher.kt:133`.
   - **The share sheet** keeps working: it presents from `LocalUIViewController`, which is now Hopi's controller (`Platform.ios.kt:32-36`).
   - **JVM.** No inspector runtime. `isAvailable` is false and the desktop viewer never calls it.
   - The above is a design reading of the plan. Nothing exists in code yet (verified: `rg -n HopiInspector -g '!**/build/**' -g '!docs/**'` finds nothing).
