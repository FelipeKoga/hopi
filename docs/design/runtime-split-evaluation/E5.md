**Consequences the plan does not state:**
- **Android never passes `summaryLog` or `remoteControl` to perf today** (verified). `PerfEntry.boot` sets only the threshold and the heartbeat (`AndroidBackend.kt:268-271`), and the DSL has neither field (`HopiPerfExtension.kt:16-25`). So on Android perf lines are always on and remote control always allowed, unless app code calls `HopiPerf.install { summaryLog = false }`.
  - With a global `summaryLog`, `hopi { summaryLog = false }` (`gradle-plugin/.../HopiExtension.kt:32`) would newly silence perf lines. The README must say so.
  - `remoteControl` needs a DSL field before it can be set on Android at all.
- **Every `install` or `start` call re-applies all five settings today, with defaults for the unset ones**, through `configure(PerfSettings(config.…))` (`PerfRuntime.kt:293-295`) (verified by reading; no test covers it). So `PerfLab`'s `start` (`PerfLab.kt:148-154`) resets a plugin `hangThresholdMs = 300` back to 250, and resets the threshold or interval of an earlier remote `perf.start` (`BridgeSession.kt:318`). Recommendation: the API builder records which settings were set (as the plan does for rules builders, "builders keep what is set", plan :149), and the runtime applies only those, as the nulls of `PerfStartRequest` already mean "keep" (`PerfController.kt:105-111`).
- **The defaults become literals in `hopi-api`**, which has no dependency (D4). The runtime's defaults come from `PerfLimits` (`hopi-core/src/commonMain/kotlin/dev/koga/hopi/core/perf/PerfMonitor.kt:24,27`; `PerfSettings.DEFAULT`, `PerfRuntime.kt:42`). Today only `DefaultsParityTest` guards against drift (`hopi-perf-noop/src/jvmTest/kotlin/dev/koga/hopi/perf/DefaultsParityTest.kt:17-24`), and stage 6.3 deletes it. Replacement (recommendation): a `hopi-perf` jvmTest.
  - It captures the config with `HopiPerf.start { captured = this }`; the block runs even without a runtime.
  - It asserts `hangThresholdMs == PerfLimits.DEFAULT_HANG_THRESHOLD_MS` and `sampleIntervalMs == PerfLimits.DEFAULT_SAMPLE_INTERVAL_MS`.
  - It asserts that `HopiMonitor.entries` names follow `PerfMonitor` order.
- **Validation stays in the runtime** (`PerfRuntime.kt:330-336`, notice `:288-291`). The API accepts anything, as the noop does (`hopi-perf-noop/src/commonMain/kotlin/dev/koga/hopi/perf/HopiPerf.kt:12-14`) (verified).
- **Calls before registration** (plan :219-221, "choose in E4.4"):
  - Perf already keeps one pending value, the screen label (`PerfRuntime.kt:270-271,280,325-328`).
  - `start` needs none today because it creates the runtime itself (`:304-305` → `:275-283`). After the split, `HopiPerf.start` cannot do that (verified).
  - Recommendation for perf: the registry keeps the pending label and one pending start (the union of the monitors, the last set values), and the runtime applies them when it registers.
  - No notice line: `hopi-api` has no log sink, and a release build would print one line per call.
- **Wire and Swift:** `HopiPerfConfig` loses three properties and `HopiPerf` loses `install`, so Swift's `HopiPerf.shared.install` disappears (`hopi-perf.klib.api:22-63`). The `internal constructor` stays: once `PerfEntry` (`AndroidBackend.kt:268`) is gone the runtime never builds one. It receives the set values through the registry interface (recommendation).

#### 3. How perf registers today (Android, iOS) and how both map to the start sequence

**3.4 Correction: stage ordering (blocks stage 6 as written).**
- Stage 6.1 removes `HopiPerf.install` and says the runtime "registers its perf runtime when its tool starts" (plan :668-670). The tool interface and the start sequence come only in stage 7.2 (:688-689).
- Between stages 6 and 7, Android still boots perf through `PerfEntry` (3.1.6), but iOS has no path at all:
  - `hopi-urlsession` has no edge to `hopi-perf` (`hopi-urlsession/build.gradle.kts:48,56`);
  - `HopiPerf.start` in `hopi-api` cannot create the runtime.
  - So stage 6's own [run] `-verifyPerf` on the simulator (:679-681) would find no monitor.
- Stage 5.2 handles the same problem for rules ("the start path that exists at this point", :655-657); stage 6 does not.
- Fix, either:
  - run stage 7 (start sequence and `HopiTool`) before stage 6; or
  - keep an interim `@HopiInternalApi` perf start in `hopi-perf` during stage 6, which the sample's Swift calls inside `#if DEBUG` until stage 7 replaces it.

#### 5. Native library linkage when `hopi-perf` is linked only in Debug frameworks

**How it is built and shipped** (verified):
- `hopi_perf.m` is compiled per iOS target with `xcrun clang -fobjc-arc -fmodules -O2 -target arm64-apple-ios15.0[-simulator]` and archived as `libhopi_perf.a` (`hopi-perf/build.gradle.kts:77-109`). It is wired into the cinterop `perf` with `-libraryPath` (`:51-61`).
- `hopi-perf/src/nativeInterop/cinterop/perf.def:5-6` declares `staticLibraries = libhopi_perf.a` and `linkerOpts = -framework Foundation -framework QuartzCore -framework UIKit`. The archive and its link options therefore travel inside the cinterop klib, and consumers need no linker setup (`hopi-perf/build.gradle.kts:52-53`).
- It is published as `-cinterop-perf.klib` (`build.gradle.kts:259`), which `checkPublication` checks.
- The library defines C functions and one Objective-C class, `HopiPerfCadence` (`hopi-perf/src/nativeInterop/objc/hopi_perf.m:491-499`, the `CADisplayLink` target). It has no `+load` and no constructor attribute (grep).

**Debug-only linking:**
- Linking follows the dependency. A framework link whose libraries do not include `hopi-perf` never sees `libhopi_perf.a`. The framework for the Xcode Release configuration is built without `hopi.enabled` (`project.yml:75-79`), so it has neither.
- The documented measurement, not re-run here: without the flag, 0 `_hopi_perf_` symbols and 0 `HopiPerfCadence`; with it, 79 `_hopi_perf_` symbols, 491 perf Kotlin symbols and 24 class symbols (`perf-monitors.md:927-932`).
- The 24 `HopiPerfCadence` lines prove the archive member is merged into the static framework's `Shared` binary: no Kotlin code names that class (grep), so only `hopi_perf.o` can define it. The 79 count alone would not prove it, because `nm -m` also lists undefined references.
- The same measurement shows the hazard of plan 3.6.1 item 1 for perf: `linkReleaseFrameworkIosSimulatorArm64` with `-Phopi.enabled=true` contains the whole library. The release guard must treat `hopi-perf` (the project, or `dev.koga.hopi:hopi-perf*`) like any other runtime (unverified: the guard is not built yet; X2).
- **App link:** Debug sets `DEAD_CODE_STRIPPING: NO` (`project.yml:57-61`), so every member pulled in stays. The sample passes no `-ObjC` (`project.yml:44-54`). An app that does (CocoaPods' default) loads every Objective-C member of a static framework, so `HopiPerfCadence` would land even with no Kotlin perf code reachable (unverified: no such app here).
- Whether a `hopi-perf` on the Debug classpath that nothing references still lands in the binary is E2.3's [run] (experiment X1 below, from the perf side). With option D the entry names the tool, so it is kept by design. Today the sample keeps it through `export(perfModule)`, as its comment says (`sample/shared/build.gradle.kts:85-86`).

**Other points:**
- **Minimum iOS:** `hopi-perf` hard-codes `15.0` (`hopi-perf/build.gradle.kts:85-86`), and only `hopi-core`'s `urlSessionMinIos` is checked against Kotlin/Native's minimum (`hopi-core/build.gradle.kts:62-64,98-113`) (verified). If E2.6 moves the URLSession library, move that check with it and make perf use the same constant (recommendation).
- **Two Kotlin frameworks** in one app that each include `hopi-perf` would carry two `HopiPerfCadence` classes and duplicate `_hopi_perf_*` symbols (unverified: not in this repository; a pre-existing limitation).
- **Doc correction:** `docs/ARCHITECTURE.md:70-72` says the perf binding has "no Objective-C class". That is true of the cinterop binding (`headerFilter = hopi_perf.h`, C only, `perf.def:3-4`), but the library defines `HopiPerfCadence`, and the release check scans for it (`sample/shared/build.gradle.kts:164`).
- **Plan correction:** 3.6.1's summary of the iOS check (plan :298) leaves out two of its perf assertions: no `HopiPerfCadence` class, and no `kfun:dev.koga.hopi.perf.internal` symbol (`sample/shared/build.gradle.kts:163-164`).
