**How `maxBodyBytes` and the other store settings reach OkHttp capture today** (verified):

1. Build time only. Values from `hopi { }` → task inputs (`HopiPlugin.kt:90-98`) → literals
   (`GenerateHopiConfig.kt:63-71`). Android has no run-time setter.
2. In the provider: `Settings` (`HopiInitProvider.kt:139-151`) → `AndroidCapture.start` validates the
   caps (invalid caps give a notice and nothing starts, `AndroidCapture.kt:120-124`) and stores them
   once (125-127; a second `start` returns early). No store exists yet (`HopiInitProvider.kt:16-17`).
3. On the first recorded request (`HopiOkHttpInterceptor.kt:53`, `UrlConnectionRecorder.kt:117, 149`,
   `OkHttpRules.kt:47`), `AndroidCapture.target()` → lazy `installed` (`AndroidCapture.kt:87-101`)
   → `CaptureInstallation.install` (`hopi-core/src/commonMain/kotlin/dev/koga/hopi/core/capture/CaptureInstallation.kt:24-50`):
   - `maxEntries`, `maxTotalBytes`: `HopiStore.configureDefault`. The first creator wins and later
     calls return the store unchanged (`HopiStore.kt:765-779`); a read of `HopiStore.default` that
     comes first creates it with 500 / 16 MiB (766-767).
   - Redaction: the union of every installation's settings (`includeRedaction`, CaptureInstallation.kt:37-43).
   - `summaryLog`: one process sink (45-46, 67-72). `agentBridge`: `AgentBridgeHook.requestStart`
     once per process (47; `AgentBridgeHook.kt:33-36`).
   - `maxBodyBytes`: **per installation**, `min(maxBodyBytes, store.maxTotalBytes / 2)` (49) →
     `Target.maxBodyBytes` (`AndroidCapture.kt:85, 100`), read at `HopiOkHttpInterceptor.kt:139,
     142, 341` and `UrlConnectionRecorder.kt:308, 318, 483`.
4. The Ktor plugin is a second installation, made when the client is created (`hopi-ktor/src/commonMain/kotlin/dev/koga/hopi/ktor/Hopi.kt:44-60`).
   The sample's order: the provider stores settings only; `MainActivity.onCreate` copies the
   `--el maxBodyBytes/maxTotalBytes` extras into `SampleHttp` (`MainActivity.kt:101-106`) and calls
   `SampleHttp.start()` (108), which builds the client with `install(Hopi) { Summary; agentBridge =
   true; caps }` (`SampleHttp.kt:64-75`). That makes the Ktor plugin the first installation: its caps
   create the store, and it starts the sink and the bridge. The sample has no `Application` class and
   its manifest declares only `MainActivity` (`sample/androidApp/src/main/AndroidManifest.xml:6-18`).
   (unverified: that no library makes a recorded request earlier.) OkHttp capture covers Ktor's
   OkHttp engine (`AndroidCapture.kt:129-131`), so the plugin defers (`Hopi.kt:88-89`), and OkHttp
   capture records the request with its own cap, min(256 KiB from `hopi { }`, store / 2). So
   `--el maxTotalBytes` reaches the store, but `--el maxBodyBytes` reaches only the Ktor recorder,
   which records only pass-through requests (those that name `Accept-Encoding`, `Hopi.kt:89,
   107-108`). This matches `docs/ROADMAP.md:146-151` and `docs/ARCHITECTURE.md:1805-1808`.
5. iOS: the launch arguments go into the run-time configuration of `HopiUrlSession.start`
   (`sample/iosApp/iosApp/iOSApp.swift:10-17`) and also into SampleHttp's copies
   (`MainViewController.kt:25-26`). A run-time path remains on iOS after D6.

a `capBytes` that nothing applies), `benchmark/device/scripts/giant.py:7-8, 45-48`,

Two more consequences the plan does not list (verified by reading every call site of
`requestStart(` and `CaptureInstallation.install(`):

- **Bridge timing.** On Android, today the bridge starts from AndroidCapture's lazy installation (first
  recorded request), from the Ktor plugin, or from `PerfRuntime.install` with `agentBridge`
  (`hopi-perf/src/commonMain/kotlin/dev/koga/hopi/perf/internal/PerfRuntime.kt:296`). The provider's perf boot passes no `agentBridge`
  (`HopiInitProvider.kt:102`; `AndroidBackend.kt:268-271`; the default is false, `HopiPerf.kt:80`).
  The sample masks this: `SampleHttp.start()` is there "so the agent bridge is up before the first
  request" (`SampleHttp.kt:79-82`). Without `install(Hopi)`, `hopi { agentBridge = true }` brings the
  bridge up only after the first recorded request: the CLI, the desktop viewer and `hopi perf start`
  cannot connect before then. iOS starts eagerly (`UrlSessionCapture.kt:127`).
- **Store caps.** Once the Ktor plugin no longer comes first, any code that reads `HopiStore.default`
  before the first recorded request creates the store with default caps and silently ignores
  `hopi { maxEntries; maxTotalBytes }`: opening the inspector (`HopiScreen.kt:105`; the launcher
  resolves the store only when it opens, `HopiLauncher.kt:85-86`), `mock { fromTransaction }`
  (`HopiRules.kt:41`), and `PerfRuntime.kt:296`. The same hazard is already latent today for
  OkHttp-only apps.

**Recommendations.**
- Start sequence (stage 7). At provider time, preset the default store's caps without creating the
  store, e.g. a `@HopiInternalApi` preset read by `configureDefault()`. The store's constructor starts
  the `hopi-store` thread (`HopiStore.kt:263-265`), which today is deliberately kept off the startup
  path. With `agentBridge = true`, start the bridge at start: either an eager installation on a
  background thread, or a bridge that binds at start and resolves the store on the first connection.
  Give perf `agentBridge` and `summaryLog` from the global configuration (plan 3.3).
- The sample's caps (stage 3). **Recommended:** Gradle properties feed the block, for example
  `maxBodyBytes.set(providers.gradleProperty("sample.maxBodyBytes").map(String::toLong).orElse(256L * 1024))`,
  and the same for `maxTotalBytes`. DeviceViewerUiTest's precondition (KDoc 49) and launch (87) become
  "debug build installed with `-Psample.maxBodyBytes=8388608`" (8 MiB is 16 MiB / 2, so the default
  store cap is enough). `giant.py` and `ui_hold.py` replace `--cap`/`--store` with build and install,
  and GiantJson's header reads a build constant. Cost: one install per cap value. **Alternative:** a
  debug-only run-time override of the per-body cap, called from a `src/debug` source set (because
  `MainActivity.kt` also compiles for release) before the first recorded request. It works only for
  the per-body cap if the store is created at start for the bridge; its ordering is fragile and it
  adds internal API. Use it only if the sweeps must change the cap without reinstalling. iOS keeps its
  run-time path.
- Check for the recommended fix (to run after stage 3): `./gradlew :sample:androidApp:installDebug -Psample.maxBodyBytes=8388608`,
  `adb reverse tcp:8765 tcp:8765`, start the dev server (`sample/devserver/devserver.py`), then
